# Експеримент: обрив живлення під час запису конфігу

## Мета

Перевірити, що конфігурація переживає некоректне завершення запису: після обриву живлення посеред транзакції пристрій має завантажитися з цілісним конфігом — старим або новим, але не з частково записаним.

## Що захищає конфіг

Конфіг зберігається у NVS одним ключем (`blob`) як цілісна структура:

```cpp
void persist() {
  prefs.putBytes(BLOB_KEY, &current, sizeof(current));
}
```

Це принципово. Початкова реалізація писала три окремі ключі підряд:

```cpp
prefs.putUShort("cfgVersion", ...);
prefs.putUShort("dblClickMs", ...);
prefs.putChar("txPowerDbm", ...);
```

NVS гарантує атомарність запису **одного ключа**, але не групи ключів. Обрив живлення між другим і третім викликом залишив би нове значення `dblClickMs` при старому `txPowerDbm` — кожне поле окремо валідне, конфіг у цілому неузгоджений. Перехід на один блоб переносить гарантію атомарності на всю структуру.

Механізм гарантії: NVS в ESP-IDF — log-structured сховище. Запис не змінює наявний запис на місці, а додає нову версію в кінець логу і лише потім позначає стару як застарілу. Якщо живлення зникло між цими діями, при наступному монтуванні NVS бачить незавершений запис без валідної CRC і просто його ігнорує — активною лишається попередня версія.

Додатковий захист при читанні — перевірка розміру блоба:

```cpp
size_t storedSize = prefs.getBytesLength(BLOB_KEY);
if (storedSize == sizeof(ValuesV1))      { /* міграція v1 -> v2 */ }
else if (storedSize == sizeof(Values))   { /* читаємо v2 */ }
else                                     { /* дефолти */ }
```

Блоб несподіваного розміру не потрапляє в структуру, а відкидається на користь дефолтів. Розмір блоба водночас є ознакою версії формату: v1 займає 4 байти, v2 — 5 байт. Обидві структури оголошені `packed`, тому їхній розмір є частиною формату на диску, а не деталлю реалізації компілятора:

```cpp
static_assert(sizeof(Values) == 5, "Config blob layout must stay stable");
```

## Методика

1. `config get` — зафіксувати поточне значення
2. `config set double_click_window_ms <нове значення>`
3. Протягом ≤50 мс після Enter від'єднати USB-кабель
4. Під'єднати назад, дочекатися старту
5. `config get` — перевірити, з чим завантажився пристрій

Значення чергувалися між 700 і 300, щоб кожен цикл змінював стан і результат був однозначно інтерпретованим.

## Висновок

У жодному циклі не вдалося отримати пошкоджений або частково записаний конфіг. Пристрій щоразу завантажувався з цілісним значенням, `cfg_version` лишався коректним, рядок `Config loaded:` був присутній у логу (конфіг прочитано, а не відкинуто), POST проходив із маскою `0x00`.

**Обмеження експерименту.** Вікно запису `putBytes()` для 5 байт — одиниці мілісекунд, тому вручну влучити точно в момент транзакції складно: в усіх циклах запис встигав завершитися до обриву. Коректне формулювання результату: за проведену кількість спроб не вдалося отримати пошкоджений конфіг. Гарантію дає архітектура NVS, а експеримент лише не знайшов їй спростування.

Для строгої перевірки потрібне програмоване реле або MOSFET-ключ, що рве живлення за таймером із точністю до мілісекунд, і прогін у тисячі циклів — саме так подібні властивості перевіряють у промисловому тестуванні.
